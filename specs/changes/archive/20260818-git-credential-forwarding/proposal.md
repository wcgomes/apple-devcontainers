# Proposal: Git credential forwarding into the container on create paths

> **Amendment 1 (2026-08-18):** username-agnostic container-side credential helper — decision B. Replaces the container-side mechanism of decision (d): instead of configuring `credential.helper store`, the seed exec now writes a POSIX-sh credential helper into the container and appends it via `git config --global --add credential.helper <absolute-path>`. Decisions (a), (b), (c), (e) unchanged; clone keeps its own `credential.helper store` + approve mechanism.

## Intent

Reported failure: a bind-mode workspace whose `postCreateCommand` runs `git clone https://plantsuite@dev.azure.com/plantsuite/PlantSuite/_git/GitOps` inside the container fails with `could not read Password ... No such device or address` — no TTY and no credential helper in the guest — even though the host has working credentials for `dev.azure.com`. `clone` (volume mode) already solves this for its primary repo (host `git credential fill` → one-shot in-container auth → `credential.helper store`); `up`/`rebuild` create paths have no equivalent, so create-path hooks that need HTTPS git fail on fresh containers. This change seeds the connection user's git credential store in the container on the create paths of `up` and `rebuild`, before any create-path lifecycle hook runs, using HTTPS credentials obtained from the host.

## Scope

- Create-path seeding guarantee (normative detail in spec.md): paths (`up` bind fresh create; `rebuild` replacement create, bind and volume mode), timing (after the create-path ownership steps, before any create-path lifecycle hook), discovery (bind: host workspace remotes via `git -C <hostWorkspace> remote -v`; rebuild volume: stamped `devcontainer.git_url` label), matching per (protocol, host, username) with no path component, store shape (container-side POSIX-sh credential helper: script 0700 in the connection user's home + `git config --global --add credential.helper <absolute-path>` append + `git credential approve` per unique entry; helper store file 0600 — Amendment 1), silent-skip cases, soft-fail semantics, redaction, non-create exclusion, and clone covered-by-design regression.
- Routing: ADDED requirement in `specs/core.md` (shared create-path invariant) + MODIFIED requirement in `specs/clone.md` (**In-container full clone populate (auth by URL scheme)**) declaring the shared acquisition contract reused by seeding.
- Reuse: `HostGitCredential.fillHTTPS` (incl. `GIT_TERMINAL_PROMPT=0`, `ADEVCONTAINER_GIT_TOKEN`, `gh auth token` fallback), `GitURLClassifier.httpsCredentialFields`, `HostGitClient.redactURLUserinfo`, and clone's in-container `git credential approve` script pattern — the store config is replaced by the container-side helper script (Amendment 1).
- Planning only: no source-code changes, no tests, no wiki edits, no commits in this bundle. Execution is planned test-first in tasks.md with the suite of record `swift run adevcontainerTests` (integration suites skip on Linux).

## Non-goals

- No seeding on non-create paths: `up` reuse of a running matching container, `up` start-stopped, and bare `start` MUST NOT seed.
- No clone mechanism change: clone's populate keeps its own store+approve; no second seeding call on `clone` (regression coverage only).
- No SSH credential seeding; SSH remotes stay out of scope.
- No PAT/token CLI flags; `ADEVCONTAINER_GIT_TOKEN` remains an env escape hatch only.
- No GCM-in-guest and no mounting of the host `~/.git-credentials`.
- `up` MUST NOT gain a host-git prerequisite (bind `up` works without host git today; seeding silently skips).
- No change to hook semantics, delete-on-fail policy, ownership, or bring-up recovery.

## Approach

New helper `GuestGitCredentialSeed` (Sources/ADevContainerLib/Git/GuestGitCredentialSeed.swift) with call sites in UpCommand (after ownership, before hooks) and RebuildCommand (after ownership, before hooks, both modes; volume source = stamped `devcontainer.git_url`). Bind mode discovers the host workspace's unique HTTPS fetch remotes via `git -C <hostWorkspace> remote -v`; rebuild volume mode uses the stamped git URL. Credentials come from the host through the existing `fillHTTPS` contract; the helper emits an in-container seed script that writes a POSIX-sh credential helper (get/store/erase) to the connection user's home, appends it via `git config --global --add credential.helper <absolute-path>`, and `git credential approve`s one entry per unique (protocol, host, username) — secrets travel via environment/stdin, never argv (Amendment 1 supersedes the earlier `credential.helper store` approach). All skip and failure semantics follow the decision index below.

## Decision index

- **(a) Create-paths-only scope:** seed on `up` bind fresh create and `rebuild` replacement create (bind and volume mode), before create-path hooks. Rejected alternative: seeding on all `up` paths and `start` — existing containers predate the failure and their hooks already ran, re-seeding on every resume adds an exec per resume and could overwrite in-container credential changes, and `rebuild` is the remediation for pre-change containers.
- **(b) Soft-fail seeding semantics:** seeding failures warn on stderr and the create path continues; seeding MUST NOT delete the container and MUST NOT enter bring-up recovery. Why not hard-fail: seeding is best-effort convenience — a missing in-container git or transient exec failure must not destroy a freshly created container; the create path's own hooks keep their delete-on-fail semantics, so a hook failure remains the hook's own error. Consistent with rebuild's existing soft-fail ownership semantics.
- **(c) Routing:** ADDED requirement in core.md (shared create-path invariant: paths, timing, discovery, matching, store shape, silent skip, soft-fail, redaction, non-create exclusion, clone covered-by-design) + MODIFIED requirement in clone.md **In-container full clone populate (auth by URL scheme)** (declare the shared acquisition contract — host fill with `GIT_TERMINAL_PROMPT=0`, `ADEVCONTAINER_GIT_TOKEN`, `gh auth token` fallback; guest store+approve; redaction — single-sourced and reused by seeding). Rationale: the acquisition contract already lives in clone.md's populate requirement and core.md owns shared create-path invariants (precedent: friendly-container-name routes to both specs). Rejected alternative: all-in-core.md would duplicate the acquisition contract; all-in-clone.md would misroute up/rebuild create-path invariants into the volume-mode spec.
- **(d) Implementation shape:** new helper `GuestGitCredentialSeed` (Sources/ADevContainerLib/Git/GuestGitCredentialSeed.swift) + call sites in UpCommand (after ownership, before hooks) and RebuildCommand (after ownership, before hooks, both modes; volume source = stamped `devcontainer.git_url`). Reuses `HostGitCredential.fillHTTPS` (new `credentials: any GitCredentialProviding = HostGitCredential()` seam on UpCommand.run and RebuildCommand.run, mirroring CloneCommand.swift:44), `GitURLClassifier.httpsCredentialFields`, and `HostGitClient.redactURLUserinfo`. **Container-side mechanism (Amendment 1, 2026-08-18 — decision B):** the seed exec (in-container script, same placement: after ownership, before create-path hooks, up fresh-create + rebuild both modes) now (1) writes a POSIX-sh credential helper script to the connection user's home in the container (e.g. `$HOME/.adevcontainer/git-credential-adev`, mode 0700, owned by the connection user), (2) configures `git config --global --add credential.helper <absolute-path>` — APPEND, never replacing existing helpers — and (3) runs `git credential approve` per unique (protocol, host, username) entry exactly as today, which routes through the configured helper whose store mode persists the entry. Helper semantics: `get` matches the persisted store by (protocol, host) IGNORING the queried username and returns the queried username (or the stored one when the query has none) plus the stored password; no match → exit 0 with no output, so git falls through to remaining helpers, askpass, or prompt; `store` persists the entry, deduping by protocol+host+username, to its own store file (e.g. `$HOME/.adevcontainer/git-credentials`, mode 0600, connection-user-owned) — the helper MAY use git's store file format with percent-encoding or its own simple line format, and persisted values MUST round-trip raw username/password values including `@`/`:` characters without corruption; `erase` is a no-op. Secrets are never echoed to stdout/stderr outside the credential protocol and never appear in argv. Rationale (observed evidence, DIAG logs 2026-08-18): host `git credential fill` returns username `wyller.gomes@plantsuite.com` (GCM keychain email) while hook URLs force `plantsuite` (Azure DevOps org as userinfo) → git-credential-store's exact username matching never matches → ENXIO at hook time; manual-terminal success came from VS Code's GIT_ASKPASS passthrough, which is absent in the non-interactive hook env. Decision B closes the whole class (any URL-forced username on seeded hosts) without secrets in the hook env and without domain heuristics. `--global` (not repo-local) because in bind mode the workspace repo is a host bind mount and repo-local config would mutate the host repo, and `--global` covers sibling repos; approve entries carry no path so any path on the host matches. Note: bind-mode remotes with explicit userinfo now additionally benefit — the helper serves fill's username AND URL-forced usernames for the same host.
- **(e) Remote discovery and silent skip:** bind = `git -C <hostWorkspace> remote -v` (unique fetch URLs); rebuild volume = stamped `devcontainer.git_url`. No git repo / no remotes / missing host git / nil fill → silent skip (no warning, no failure): `up` MUST NOT gain a host-git prerequisite and public repos stay anonymous.
