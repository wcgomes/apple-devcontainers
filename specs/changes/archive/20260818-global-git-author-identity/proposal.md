# Proposal: Global Git author identity for clone and rebuild

## Intent
`clone` currently applies the chosen Git author identity to the primary repository only, while a replacement `rebuild` creates a new container without rehydrating the identity that is already persisted in the workspace repository. As a result, repositories cloned by create-path hooks in the new container do not reliably inherit the workspace's chosen author identity. This change makes the workspace-local identity available globally to the resolved connection user while keeping the local repository configuration authoritative.

## Scope
This change covers the distinct author-identity behavior of initial `clone` creation and ordinary `rebuild` replacement for existing workspaces in both bind and volume modes. A complete identity on initial `clone` MUST continue to be written locally and MUST also be synchronized to the created container's connection-user global Git config; `rebuild` MUST capture a complete local pair before replacement begins in both modes and synchronize it to the new container before create-path hooks. Bind rebuild capture MAY use the host workspace, but volume rebuild capture MUST read the existing workspace inside the old container, or another source that remains valid until old-container deletion, and MUST NOT use a host GitClient path. The normative delta modifies the realized clone author-identity requirement and adds the shared rebuild rehydration requirement to the core lifecycle contract. This bundle was separate from the `git-credential-forwarding` bundle and MUST NOT modify it.

## Non-goals
- Adding author-identity synchronization to `up` fresh-create; the approved outcome names initial `clone` creation plus `rebuild`, and the existing `up` create path remains outside this change.
- Replacing local repository configuration with global-only configuration, changing Git precedence, or rewriting local identity during `rebuild`.
- Prompting during `rebuild`, inventing defaults, synchronizing incomplete identities, or requiring a persisted container HOME.
- Changing the host Git configuration, other container users' Git configuration, labels, credential files, credential-helper behavior, current credential seeding, or current `[DIAG]` work.
- Changing existing clone author resolution, environment overrides, TTY confirmation/collection, lifecycle hook failure cleanup, or rebuild recovery behavior except that global identity-sync failure is warning-and-continue.

## Approach
Retain the current clone identity resolution and local application, then write the same complete pair at global scope as the resolved connection user in the new container. For `rebuild`, capture local-only `user.name` and `user.email` before the Phase B replacement boundary at `RebuildCommand.swift:423`: bind mode may use an injectable host-workspace reader, while volume mode must use an injectable runtime/guest reader against the old container's mounted workspace and must not fall back to a host GitClient path. After the replacement is started, perform the global write after the existing ownership, credential-seeding, and `[DIAG]` work and before `runCreatePathThroughWaitFor` (currently `RebuildCommand.swift:843-851`). Add runtime/guest-reader seams, host and guest fixtures, and exact event-order assertions so the old-container read precedes deletion/replacement. Use a narrowly scoped shared guest identity writer so clone and rebuild share value handling and failure semantics without introducing a general Git configuration abstraction. Incomplete reads are a no-op for global synchronization, while a global write failure is warning-only: it MUST not delete the replacement container or workspace, invoke BringUpRecovery, create or use a recovery helper, prompt, or skip the existing replacement flow and hooks.

## Live-contract check
The realized `specs/clone.md` requirement currently describes local author application after populate and before hooks; this change modifies that requirement to add the connection-user global write without removing the local source of truth. The archived `git-credential-forwarding` delta owns HTTPS credential acquisition/seeding and remains untouched; the identity write is limited to `user.name` and `user.email` and does not alter credential helpers or `[DIAG]` behavior. The active `workspace-parents-writable` delta owns ownership preparation before hooks, so identity synchronization composes after the existing preparation. The active `friendly-container-name` delta owns container naming and resource identity and has no overlap. The realized core lifecycle contract already places rebuild replacement create/start and create-path hooks after the pre-delete gate; the new capture-before-delete and sync-before-hook ordering fits that contract. The live branch places rebuild Phase B at `RebuildCommand.swift:423`, old-container deletion at `:425-438`, ownership at `:635-678`, credential seeding at `:680-698`, `[DIAG]` work at `:700-777`, and `runCreatePathThroughWaitFor` at `:843-851`; clone populate/author/hooks remain at `CloneCommand.swift:487-559` and `:880-915`. Existing `RebuildScenario` and clone/rebuild command tests will be extended with injectable host/guest readers and explicit cleanup/recovery regressions.

## Decision index
- **Bounded change:** `global-git-author-identity` was opened as a separate bundle because local/global author identity is a different bounded behavior from HTTPS credential forwarding; do not edit `git-credential-forwarding`.
- **Clone persistence:** Keep local `.git/config` as the primary repository persistence and add the same complete pair to the resolved connection user's global Git config so sibling repositories inherit it.
- **Rebuild source:** Read only the existing workspace repository's complete local identity before the destructive replacement boundary; bind mode reads the host workspace repository through the host reader, while volume mode reads the existing workspace inside the old container through a runtime/guest reader. Volume mode MUST NOT use a host GitClient path, and global config is never the source of truth.
- **Rebuild destination and timing:** Write the captured pair to the new container's resolved connection user's current global Git config after existing ownership, credential-seeding, and `[DIAG]` work and before create-path hooks, even when HOME is not persisted and even when existing global values differ.
- **Shared primitive:** Use one narrow guest identity writer for global `user.name`/`user.email` updates; keep host/local identity acquisition command-specific and do not create a general Git configuration abstraction.
- **Completeness and prompts:** Synchronize only a complete name/email pair. Rebuild never prompts; initial clone retains its current prompt/collection and incomplete non-interactive warning behavior.
- **Failure semantics:** Local clone identity behavior remains intact. A global synchronization failure emits only its warning and continues through the existing replacement flow and hooks without deleting the replacement container or workspace, invoking BringUpRecovery, creating or using a recovery helper, or prompting; the ordinary one-time deletion of the old rebuild container remains unchanged.
- **Regression contract:** Explicit tests cover clone populate and author-write failures, clone hook cleanup and successful hook continuation, and rebuild hook cleanup/recovery and successful hook continuation; these behaviors are not covered only by an indirect review.
- **Isolation:** Affect only the resolved connection user in the container; never modify other users, the host Git config, labels, or credential files.
- **Scope boundary:** `up` fresh-create is intentionally out of scope because the approved wording and existing plan specify initial `clone` creation plus `rebuild`; no additional create path is inferred.
- **No design document:** The two source paths, one ordering rule, and explicit failure/isolation decisions fit in this proposal, delta, and task plan without design overflow.

## Clarifications
- **Q:** Is `up` fresh-create included so sibling repositories cloned during that path inherit the identity?
  **A:** No. The approved behavior is initial `clone` creation plus ordinary `rebuild`; `up` fresh-create remains unchanged. No source evidence requires expanding this bundle to another create path.
- **Q:** What is a valid local-identity source for volume-mode rebuild?
  **A:** The complete local pair MUST be read from the existing old container's mounted workspace, or another source that remains valid before old-container deletion. A host workspace path or host GitClient read MUST NOT be used for a volume workspace, even when a label contains a host-looking value.
