# Proposal: `rebuild` subcommand — rebuild a managed container from its current config

## Intent

Today a managed container that has drifted from an edited `devcontainer.json` can only be replaced by deleting it and re-running `up`/`clone` (losing the named volume or requiring manual re-setup). `up` on config-hash mismatch fails closed with `config_hash_mismatch` and does not offer a force-rebuild flag. This change adds **`adevcontainer rebuild`**, the sole user-forced rebuild of an existing managed container that reads the **current** `devcontainer.json` (committed or not) through the same dual-mode reader used by `start`, runs the full create path like a fresh `up`/`clone`, and — the core invariant — creates a new container **without deleting or replacing already-declared volumes**: the workspace `*-ws` volume and config `type=volume` named volumes are reused with their data. When a rebuild has already deleted the old container and hard provisioning fails, the command also provides a bounded recovery session that restores edit access to the stamped config; this is a recovery session, not an exact rollback of the old container, image, or filesystem state. Clone-origin volume recovery uses a helper container on the preserved `*-ws` volume; bind-mode recovery opens the host stamped config path directly with the same TTY/non-TTY operator experience and no helper.

## Scope

- Change id: **`rebuild`**
- Package root: repository root (Swift SPM `adevcontainer`)
- Library under `Sources/ADevContainerLib/`; CLI entry `Sources/adevcontainer/AdevcontainerMain.swift`; tests under `Tests/adevcontainerTests/`
- Realized base contract: union of `specs/<domain>.md`. This delta **adds** the `rebuild` command surface, the strict dual-mode config read, and the forced-rebuild/volume-preservation contract; **modifies** the **Unified managed selection for lifecycle commands** model (rebuild joins the `--name`/picker set; `-w` remains usage-error), the **Up lifecycle (create, start, reuse)** drift policy and create-path hook matrix (`up` hash mismatch → `config_hash_mismatch` error hinting `rebuild`; equal-hash and forced rebuild only via `rebuild`), the **Volume-mode workspace mount and labels** freshness rule (re-clone carve-out applies to `clone` only), the **Optional `--vscode` flag** and **postAttachCommand policy (CLI-only)** command lists (rebuild accepts `--vscode` with identical gates), and the **Derived image build** reuse clause (derived-tag reuse when material unchanged applies to rebuild).
- Commands affected: new `rebuild`; existing `up`, `clone`, `start`, and ordinary `delete` behavior is unchanged. `list`/managed selection render marked recovery helpers (volume path only), and ordinary `prune` protects them and their referenced volumes.
- Config read mechanism: reuse/extract the existing dual-mode reader in `Sources/ADevContainerLib/Commands/PostAttachConfigLoader.swift` (`loadBindMode` labels → host file → `ConfigResolver.resolve`; `loadVolumeMode` exec `cat` → temp file → `ConfigResolver.resolve` with `workspaceFolderBasename`) with **strict** semantics for rebuild: unreadable/missing config is a structured `CLIError` (`config_not_found` / `config_parse`), never a silent nil.
- Recovery eligibility (mode-split):
  - **Volume clone-origin:** a managed volume-mode container with the existing clone-origin identity stamps (`devcontainer.workspace_mode=volume`, non-empty `devcontainer.git_url`, `devcontainer.workspace_volume`, and stamped config path) may enter helper-based recovery.
  - **Bind (`up`-origin):** a managed bind-mode container with stamped `devcontainer.local_folder` + `devcontainer.config_file` may enter host-editor recovery after the same hard post-delete failures. No helper container, no Alpine image preflight, and no volume mount or atomic helper write.
  - Non-clone volume targets (volume mode without clone-origin stamps) do not enter recovery.
- Recovery outcome: after old-container deletion, only new-container create/start failure and `onCreate`/`updateContent`/`postCreate`/`postStart` failure offer recovery. Settings/extension soft-fail, VS Code open soft-fail, and `postAttach` failure retain their existing semantics and never start recovery. Pre-delete failures (including parse/`config_not_found`) still fail closed with the old container untouched.
- Recovery helper (volume only): an immutable arm64-pinned lightweight Alpine helper image is preflighted before the old container is deleted. The helper mounts the exact existing `*-ws` volume read-write, retains managed identity/name labels, is visibly marked as recovery, and is protected from ordinary prune. Bind recovery MUST NOT create a helper or attach recovery labels to any container.
- Recovery editing:
  - **Shared TTY gate (bind + volume):** On an eligible hard post-delete failure when stdin is a TTY and `--json` is absent, recovery MUST **not** auto-open the editor. It MUST first print the structured failure/reason clearly on stderr (same information quality as non-TTY retain), then prompt whether to open the recovery editor now with default **Y** (Enter confirms open; `n`/`N` declines). Affirmative → mode-appropriate editor flow. Decline / EOF / non-affirmative → defer path that **retains** recovery state and prints the same structured recovery details + exact `rebuild --name` retry instructions as non-TTY retain, then exits non-zero.
  - **Volume:** After an affirmative prompt, TTY recovery keeps the raw in-volume config in a private host temp session, uses `$VISUAL`, `$EDITOR`, `/usr/bin/nano`, then `/usr/bin/vi`, validates with the volume reader's rules, atomically writes and verifies the volume copy through the helper, and retries until success or cancellation. Defer/cancel retains helper+session. Non-TTY and `--json` never edit or prompt; they leave the helper/temp session and return structured details plus exact edit/retry/cleanup commands (including helper container-only delete).
  - **Bind:** After an affirmative prompt, TTY recovery opens the editor **directly** on the host stamped config path (`local_folder` + `config_file`). Validation uses bind-mode strict resolve rules. Invalid content reopens the editor without starting rebuild. Defer/cancel leaves the host file as the user left it and retains resume stamps + host path for later retry (nothing to retain except that file and the printed retry instructions). Non-TTY and `--json` never edit or prompt; they return structured recovery details with the host config path, failure kind, shell-quoted edit hint, and `adevcontainer rebuild --name ...` retry. Cleanup commands MUST NOT mention helper delete. Prefer direct host-path editing (no private temp copy required for the edit target); session metadata MAY still record baseline hashes for optional conflict awareness without inventing a helper write path.
- Docs task: README section, usage help row, and `printCommandHelp("rebuild")` updated with the command, flags, selection, volume-preservation behavior, and mode-split recovery UX.

## Non-goals

- Deleting, replacing, or re-populating the workspace `*-ws` volume, or deleting config `type=volume` named volumes, during rebuild (they are reused with data)
- Running git re-clone or `git pull` inside a volume-mode workspace during rebuild (no populate step)
- Config path migration: v1 reads the stamped `devcontainer.config_file` path; a config file that moved is a `config_not_found` error, not a discovery search
- Changing ordinary `delete` / `prune` volume semantics (rebuild and recovery use the existing container-only delete contract; recovery helpers are the explicit prune-protected exception for the volume path only)
- Rebuilding containers that are not managed (`devcontainer.managed=adevcontainer`) or whose labels are missing identity stamps
- Auto-rebuild on drift (drift still requires user action: `adevcontainer rebuild` with managed selection `--name`/auto/picker)
- General-purpose config editing or edit-confirm prompts outside the bounded recovery sessions defined here
- Exact old-container rollback, image rollback, or filesystem transaction rollback. A failed hook may have changed workspace data; recovery restores edit access only.
- Recovery for settings/extension soft-fail, VS Code open soft-fail, or `postAttach` failure
- Recovery for non-clone volume targets (volume mode without clone-origin stamps)
- Inventing a fake recovery helper container for bind mode, Alpine preflight for bind, or volume-style atomic helper write for a host file
- Concurrency protection (no rebuild serialization/locking across parallel invocations in v1)
- Full Dev Containers extension parity (no up/rebuild-driver parity claim)

## Approach

Full SDD: this proposal + outcome delta `spec.md` + `design.md` (Full mode) + dependency-ordered `tasks.md`.

1. Extract the dual-mode config reader from `PostAttachConfigLoader` into a shared `ConfigReader` with **strict** and **best-effort** modes; `PostAttachConfigLoader` keeps its tolerant behavior as a wrapper.
2. Add `rebuild` to the CLI surface: dispatch case, `--name` / `--skip-pull` / `--vscode` / `--json`, usage row, and `printCommandHelp("rebuild")`; keep the existing global `-w is only valid for up` gate.
3. Implement `RebuildCommand` in two phases with a recovery preparation gate that is **mode-split**:
   - Shared non-destructive phase: selection → stamps → strict config read (volume-mode auto-start when needed) → resolve → hostRequirements preflight → rosetta consent gate + Features fetch/build with derived-tag reuse, all **before** the old container is deleted.
   - **Volume clone-origin only before delete:** secure raw-config capture + helper-image preflight.
   - **Bind:** no helper image preflight and no private temp capture required for the edit target (host stamped path is already the source of truth).
   - Destructive create path (both modes): container-only delete of the old container → `ensureVolume` list-then-reuse → create with preserved identity → start → volume-mode git ensure / writable / ssh-forward when applicable → create-path hooks with delete-on-fail of the **new** container → settings apply → `--vscode` open → extensions → postAttach fail-keep.
   - Eligible hard post-delete failure: clean and verify any new-container attachment, then branch:
     - **Volume:** create recovery helper → print structured failure → (TTY, no `--json`) prompt open editor now? [Y/n] → yes: edit/validate/atomic-write/retry; no/EOF/non-affirmative: retain helper+temp and print non-TTY-style recovery details + `rebuild --name` retry (exit non-zero); non-TTY/JSON: recovery instructions only (helper + temp retained; never prompt or editor).
     - **Bind:** print structured failure → (TTY, no `--json`) same prompt → yes: editor on host stamped path → validate with bind-mode strict rules → retry rebuild; no/EOF/non-affirmative: retain host path/resume stamps and print non-TTY-style recovery details + `rebuild --name` retry (exit non-zero); non-TTY/JSON: structured details only (host path + edit hint + retry; no helper cleanup; never prompt or editor).
4. Test-first: unit-test `ConfigReader` strict and best-effort modes; recovery session/temp/editor/helper APIs (volume); bind host-editor recovery path; command tests with a mocked `AppleContainerRuntime` asserting deletion/volume/no-clone behavior, failure classification, mode-split recovery, retry ordering, identity/selection/prune behavior, and output; then run mocked and real Apple-container E2E coverage.
5. Document rebuild in README/help and fold the MODIFIED deltas into the domain specs.

## Clarifications

- **Q:** What CLI surface does `rebuild` expose, and does selection differ from `start`?
  **A:** New subcommand `adevcontainer rebuild [--name <container>] [--skip-pull] [--vscode] [--json]`. Selection MUST be identical to `start`: `ManagedContainers.resolveSelection` (`--name` exact match by id or name; auto-select when exactly one managed container; interactive numbered picker when multiple and stdin is a TTY; structured `selection_required` error requesting `--name` when multiple and non-interactive). `-w` / `--workspace` MUST remain a usage error on rebuild (only `up` accepts it).
- **Q:** How is the config read when the volume-mode container is stopped?
  **A:** Rebuild auto-starts it with a **bare runtime start** (no lifecycle hooks — it will be deleted anyway) before reading the config from inside the volume. If start or exec-cat fails, rebuild fails with a structured error **before anything destructive**.
- **Q:** What happens when the resolved config hash equals the stamped `devcontainer.config_hash`?
  **A:** Rebuild always proceeds — it is a user-forced rebuild, not drift detection; the derived Features tag reuse (`adev-{base}:{hash12}` when material unchanged) makes the unchanged case cheap.
- **Q:** Which identity does the new container and its workspace keep?
  **A:** Identity is seeded from the selected container's stamps — bind mode: `devcontainer.local_folder` + `devcontainer.config_file` re-resolved on host; volume mode: `devcontainer.git_url` + `devcontainer.config_file` (+ `devcontainer.workspace_volume`, `devcontainer.workspace_folder`). The new container keeps the **same container name** and mounts the **same `*-ws` workspace volume** with its data. Only `devcontainer.config_hash` (and derived labels: `workspace_folder`, `remote_user`, `config_volumes`) may change. The config path is assumed never to move (v1 reads the stamped path).
- **Q:** What is the volume-preservation invariant?
  **A:** Rebuild MUST NOT delete, replace, or re-populate the workspace `*-ws` volume and MUST NOT delete config `type=volume` named volumes. Deletion is the existing **container-only** `delete` contract on the old container; create reuses existing volumes via the runtime `ensureVolume` list-then-reuse behavior; new config volumes are created, existing ones reused. No git re-clone and no `git pull` inside the volume.
- **Q:** Does rebuild run the full create path?
  **A:** Yes, with parity to `up`/`clone` fresh create: hostRequirements preflight (fail on shortfall), rosetta consent gate + Features fetch/build with derived-tag reuse when material unchanged, `--skip-pull` honored, onCreate → updateContent → postCreate → postStart with delete-on-fail (of the **new** container), settings apply (not gated), then `--vscode` → open success → extensions apply → postAttach (fail-keep). Volume mode additionally re-injects `git:1` via `FeatureGitEnsure` (clone parity) and re-applies `ensureWorkspaceWritableByRemoteUser` only when the effective `remoteUser` differs from the stamped `devcontainer.remote_user`.
- **Q:** When is the old container deleted?
  **A:** Ordering guarantee: config read + resolution + hostRequirements + Features build complete **before** the old container is deleted. For an eligible clone-origin volume target, the secure raw-config capture plus helper-image preflight also complete before delete. Bind recovery has no helper-image preflight before delete. Any failure up to that point leaves the old container running/untouched. After delete, eligible hard create/start/create-path-hook failures clean/verify the new attachment and offer mode-appropriate recovery (volume helper session or bind host-editor session). Settings/open/postAttach and any other post-delete failure do not offer recovery. Non-clone volume targets retain warning-only post-delete behavior.
- **Q:** What output and flags are supported?
  **A:** `--json` machine-readable output (parity with `up`/`clone`), exit codes 0/non-zero, `--skip-pull` and `--vscode` supported. Volume-mode `enableSSHForward` on `CreateRequest.fromVolumeMode` only when a host ssh-agent is present (parity with the clone HTTPS branch).
- **Q:** How strict is the config read versus `PostAttachConfigLoader`?
  **A:** Rebuild uses the same dual-mode reader mechanism but with **strict** semantics: unreadable/missing config is a structured `CLIError` (`config_not_found` / `config_parse`), never a silent nil. Design decision point: a shared `ConfigReader` with strict vs best-effort modes is chosen in `design.md` (with rationale) so `PostAttachConfigLoader` keeps its tolerant behavior.
- **Q:** Which rebuild failures are eligible for recovery, and for which containers?
  **A:** The hard-failure trigger set is shared: after old-container deletion, new-container create failure, new-container start failure, or a non-zero `onCreate`, `updateContent`, `postCreate`, or `postStart` hook. Volume ensure/writable-step failures and all other post-delete failures are not recovery triggers. **Who** receives recovery is mode-split: clone-origin volume targets get helper-based recovery; bind-mode managed targets get host-editor recovery; volume targets without clone-origin stamps keep warning-only post-delete behavior. Pre-delete failures never offer recovery.
- **Q:** What must be ready before an eligible old container is deleted?
  **A:** **Volume clone-origin:** the command MUST use one immutable Alpine helper image pinned for `linux/arm64` and MUST preflight its availability before deletion; the raw in-volume config is also captured into a private host recovery session before deletion. If the image cannot be verified or made available, rebuild fails with a structured recovery-unavailable error while the old container remains untouched. **Bind:** no helper image preflight and no volume capture are required before delete; the host stamped config path remains available after delete.
- **Q:** Is the helper image selected dynamically or by a mutable tag?
  **A:** No (volume path only). The implementation MUST ship one checked-in digest-pinned lightweight Alpine reference whose manifest is verified for `linux/arm64`; runtime tag resolution and user-selected helper images are out of scope. The checked-in digest is updated only as a deliberate release change and is preflighted before deletion. Bind recovery does not use a helper image.
- **Q:** What does recovery mean, and does it roll back the failed create path?
  **A:** Recovery means restoring access to edit the stamped config and retrying the rebuild. Volume recovery edits via a helper on the preserved workspace volume; bind recovery edits the host stamped path directly. It MUST NOT promise image rollback, old-container restoration, or filesystem transaction rollback; a failed hook may have changed workspace data and those changes remain.
- **Q:** Does TTY recovery auto-open the editor?
  **A:** No. On eligible hard post-delete failure with a TTY and without `--json`, recovery MUST first print the structured failure/reason on stderr (same information quality as today's non-TTY retain), then prompt whether to open the recovery editor now. Default is **Y** (open editor): Enter or affirmative (`y`/`Y`/yes-class) confirms; `n`/`N`/no-class or EOF declines. Prompt wording and stdin line-read HOW live in `design.md` and MUST be shared for bind and volume.
- **Q:** What happens when the operator declines the editor prompt (or EOF)?
  **A:** Treat as defer/cancel of the immediate edit loop while **retaining** recovery state so a later retry works. **Volume:** keep helper + secure temp session. **Bind:** keep host stamped file as left + any resume stamps. Print the same structured recovery details and exact `adevcontainer rebuild --name ...` retry (and mode-appropriate edit/cleanup) instructions as the non-TTY retain path. Exit non-zero. Do not claim success.
- **Q:** How does TTY recovery edit and validate the config after an affirmative prompt?
  **A:** Editor selection is shared: first usable `$VISUAL`, `$EDITOR`, `/usr/bin/nano`, `/usr/bin/vi`. **Volume:** the session retains the exact raw bytes in a `0700` private temp directory and `0600` file; the editor opens that temp file; validation uses volume-mode resolution rules (including the stamped workspace basename); atomic write-back goes through the helper with readback verification; invalid resolution reopens the editor; editor cancel retains helper/temp. **Bind:** the editor opens the host stamped config path directly; validation uses bind-mode strict resolve rules; invalid resolution reopens the editor without starting rebuild; editor cancel retains nothing except the host file as the user left it (no helper to retain).
- **Q:** What happens in non-TTY and `--json` mode?
  **A:** Neither mode may launch an editor or prompt (including the open-editor-now prompt). **Volume:** the helper stays running and the secure temp file stays available; the failure result MUST include structured recovery details and exact, shell-quoted edit, `adevcontainer rebuild --name ...` retry, and container-only-delete/temp-file cleanup commands. **Bind:** there is no helper; the failure result MUST include structured recovery details with the host config path, failure kind, shell-quoted edit hint for that host path, and `adevcontainer rebuild --name ...` retry. Bind cleanup commands MUST NOT mention helper delete.
- **Q:** How is the helper selected later without destroying the recovery session?
  **A:** (Volume only.) The helper uses the original container name and copies its managed identity labels, adds `devcontainer.recovery=adevcontainer` plus an opaque recovery-session marker, and mounts the exact existing `*-ws` volume read-write. It remains visible and marked in `list`, is addressable by `exec --name` and `rebuild --name`, and is skipped by ordinary `prune`. A later named retry MUST select the helper and write the edited temp file to the volume before reading config; the helper MUST NOT be deleted before that retry unless the command is continuing in the same interactive flow. Bind recovery creates no helper, so list/prune helper rules do not apply.
- **Q:** How is edited content copied safely and verified?
  **A:** **Volume:** the host file is validated and hashed before write. The helper writes bytes to a same-directory temporary file with restrictive permissions and atomically renames it into the existing config path; `container cp` is not used. The helper reads the target back and compares the expected hash. A conflicting volume hash is copied to a second secure conflict file, the edited temp is retained, and that attempt reports `recovery_conflict` without overwriting or deleting any volume. In TTY mode the editor reopens; in non-TTY/JSON mode the next explicit named retry acknowledges the captured baseline after the operator reviews the conflict file. **Bind:** there is no volume write-back; the editor (or operator) mutates the host stamped file in place. Validation is bind-mode strict resolve of that path. Optional baseline/conflict metadata MAY be recorded in session state without requiring a private temp edit copy or helper write path; prefer direct host path as the edit target.
- **Q:** What happens after a successful retry or a recovery failure?
  **A:** **Volume:** the edited bytes are written/read back before the retry's delete gate; the helper is then removed container-only as the selected old endpoint so the final container can be created. The final container is read through its normal runtime path and MUST expose the edited config hash/content before success is reported. Because it mounts the same workspace volume, no redundant post-success copy is needed; success ensures no helper remains and removes the secure temp session. Helper creation/start/write-back/verification/cleanup failure returns a structured recovery-unavailable or rollback-style error and never deletes the workspace or config volumes. **Bind:** a successful TTY edit is already on the host path the retry reads; success reports after the normal rebuild lifecycle with no helper cleanup. Bind recovery failure (editor launch, validation loop cancel, etc.) returns structured recovery codes aligned with the volume path where applicable (`recovery_cancelled`, `recovery_unavailable`) without inventing helper-delete cleanup.
